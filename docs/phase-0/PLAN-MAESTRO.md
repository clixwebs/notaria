## 3. Resultado de la revisión de referencias

Se inspeccionaron instrucciones, README, memoria, dependencias/lock, esquema, autenticación, sedes, permisos, auditoría, reportes, estilos y componentes representativos de ElDial. Se revisaron estilos/navegación de `app-demo`, `MarketDonaNelly`, `app-inventario` y `clix-demo`, además de siete capturas.

Hallazgos que cambian la implementación:

1. **La base visual es aprovechable.** Existen tokens por marca, tablas compactas, estados semánticos, navegación, componentes de acción y diálogos. Se adaptarán al expediente y a accesibilidad.
2. **La base técnica está identificada.** Lock: Next 16.2.9, React 19.2.4, Prisma 7.8.0 y Tailwind 4.3.1. Son versiones observadas, no una selección automática para una nueva instalación.
3. **La autenticación necesita evaluación.** NextAuth está en `5.0.0-beta.31`; hay sesiones JWT y permisos orientados a rutas. El ERP exige MFA, revocación y autorización por acción/recurso.
4. **Las finanzas requieren adaptación.** El esquema usa `Float` para importes. NotariaOS usará decimales exactos y movimientos/aplicaciones consistentes.
5. **La auditoría debe reforzarse.** `logAudit` captura errores sin detener la operación; las lecturas de listas no se auditan en el clasificador inspeccionado. No se considerará suficiente para actos críticos o información reservada.
6. **SmartPSE no está acreditado como integración real.** README documenta simulación y demo real pendiente. El código sirve de referencia de contrato, XML y respuesta; deberá probarse en el entorno autorizado de la notaría.
7. **Pruebas existentes son una ventaja de método.** Se localizaron 150 archivos de prueba bajo `src`, sin ejecutarlos. Las pruebas de ElDial no demuestran el comportamiento de NotariaOS.

Evidencia y clasificación por pieza: [referencias y reutilización](01-referencias-y-reutilizacion.md). No se ejecutaron proyectos, bases ni migraciones de referencia, ni se copiaron datos o marcas a esta entrega.

## 4. Primera versión propuesta

### Recorridos provisionales

| Recorrido | Qué valida | Condición antes de operación real |
| --- | --- | --- |
| Certificación de firmas | Recepción, personas, identificación aplicable, actuación, cobro y entrega | Requisitos y evidencias aprobados para ese servicio |
| Carta notarial | Solicitud, documento, destinatarios, intentos de diligencia, resultado y constancia | Procedimiento/diligenciamiento aprobado |
| Escritura de compraventa | Representación, minuta/versiones, otorgamientos, registro, traslado y seguimiento | Catálogo de requisitos, controles y formatos validados por notario/asesor |

Son propuestas para contrastar con la demanda de la notaría. La compraventa aporta un caso protocolar completo, pero no debe convertirse en un motor jurídico que resuelva automáticamente titularidad, capacidad o suficiencia de poderes.

### Incluido en el primer producto operativo

Usuarios/MFA/permisos; configuración de notaría/oficinas; personas; expedientes/actos; requisitos/tareas/plazos; documentos/versiones; identificación habilitada y excepciones; registros/numeración; caja/anticipos/comprobantes; auditoría; protección de datos y controles PLAFT aplicables; traslados y seguimiento asistido; reportes esenciales y archivo mínimo.

### Posterior o condicionado

Portal, mensajería, agenda avanzada y modo sala de firmas completo se incorporan después del núcleo, según prioridad. El prototipo puede mostrar sus recorridos sin prometer operación. No contenciosos y custodia avanzada necesitan un alcance específico.

Se excluyen suscripciones SaaS, múltiples notarías independientes, comercio/POS/inventario, nómina, contabilidad integral, firma remota de escrituras, reconocimiento biométrico propio y automatización no autorizada de portales externos.

## 5. Arquitectura recomendada

**Monolito modular** con Next.js/React/TypeScript, PostgreSQL y Prisma como base candidata compatible con ElDial. Interfaz web, casos de uso con validación en servidor, módulos de dominio y adaptadores externos. Una BD operativa para la notaría; almacenamiento privado de documentos; trabajador de tareas durables cuando haya envíos/exportaciones.

El usuario se autentica, el servidor verifica sesión y permiso sobre el recurso, ejecuta el caso de uso y registra los efectos y la evidencia. Las operaciones críticas no dependen de que la pantalla oculte un botón.

La solución conserva separación por oficina/expediente cuando la política lo exija; no crea una base por oficina. La preferencia de oficina no concede acceso. La configuración de notaría reemplaza la necesidad de un registro comercial de tenants.

Decisiones pendientes antes del núcleo: versión soportada del stack, biblioteca/proveedor de autenticación con MFA y revocación, alojamiento/región, almacenamiento/claves, mecanismo de trabajos y componente local del lector si fuese necesario. El prototipo no depende de contratarlos.

Detalle, límites y diagrama conceptual: [arquitectura y modelo](03-arquitectura-modelo.md).

## 9. Costos y decisiones comerciales

No se contrata ni recomienda un plan concreto sin cotización y condiciones verificadas. Separar:

- Desarrollo: historias estimadas × costo del equipo + validaciones jurídica/tributaria y revisión de seguridad.
- Operación: hosting + BD/respaldo + documentos/egreso + trabajos + monitoreo + soporte.
- Transacciones: consultas de identidad + comprobantes + firma + notificaciones según uso.
- Hardware/certificados: lector, equipo, licencias y renovaciones que correspondan.

La ficha de presupuesto deberá registrar moneda, impuestos, mínimo, sobreconsumo, SLA, región y salida. Usar escenarios bajo/base/alto después de confirmar usuarios, actos y tamaño documental. Ninguna cuota gratuita de un proveedor es un costo garantizado para la notaría.
